## Questions

Support two distinct protocol shapes:

1. `item/tool/requestUserInput`: thread/turn/item identifiers and questions with `id`, `header`, `question`, `isOther`, `isSecret`, and optional label/description choices. Respond on the original server request with `{ answers: { [questionId]: { answers: [answer] } } }`. Generated schemas use `isBlocking`; `autoResolutionMs` is deprecated. Do not derive waiting behavior solely from the old timer.
2. `agentMessage` items: optional `questions: [{ title, options }]` and `delivery: "async"`. Preserve these separately from ordinary output text. The inspected client-request union has no dedicated answer RPC; prototype correlated steer/new-turn delivery before claiming full support.

Render one Telegram message per question with inline choices and a custom-answer reply path. Include option descriptions, never automatically select a recommendation, and do not suppress questions with ordinary progress output.

Add typed events/answer methods in `src/types.ts` and `src/codexAppServer.ts`; rendering and reply routing belong in `src/telegram.ts`. Reuse approval UI conventions, not approval semantics. Intercept question replies before ordinary steering/queue routing. An authorized reply to a pending question in a mention-only group should not need another mention.

Persist binding, chat, topic, requester Telegram user ID, thread, turn, question, message and resolution state. Use short opaque callback tokens. Validate authorization/topic and resolve submissions atomically. Handle duplicate clicks, `serverRequest/resolved`, interruption, disconnects, expiration and send failure. Remove resolved keyboards. A persisted RPC request ID cannot be reused on a replacement connection: expire unrecoverable requests rather than replaying them.

Collect required answers before responding once to a multi-question RPC. Secret questions must not solicit secrets in a group or log answer payloads; provide a secure local completion path.

`src/runQueue.ts` holds a global slot throughout a task. Blocking questions must not exhaust all slots: separate waiting from runnable work, preserve per-topic order and reacquire capacity before execution resumes. Nonblocking questions must not stall work.

## Goals

Proposed commands, not currently available:

```text
/goal <objective>
/goal status
/goal pause
/goal resume
/goal budget <tokens>
/goal clear
```

Use native `thread/goal/set`, `thread/goal/get`, `thread/goal/clear` and `thread/goal/updated` / `thread/goal/cleared`, scoped to the bound thread. Set `origin: "user"` only for explicit authenticated user actions. Never infer goals from ordinary tasks or invent a token budget.

Display objective, status, tokens used/budget and elapsed usage. Preserve native statuses: active, paused, blocked, usageLimited, budgetLimited, complete. Replacing the objective can reset usage accounting and needs explicit user intent. A token budget is not a dollar spending cap.

Build an app-server session supervisor independent of turns. Currently `run()` creates a client, closes the queue on completion and closes the client in `finally`. Goals need multi-turn support, changing turn IDs, ongoing question routing, idle-capacity release and fair scheduling. Do not implement goals by cron or repeated submission of the original prompt.

Prototype native continuation, pause, clear, interrupt and reconnect on the pinned runtime before fixing command semantics. Pausing a goal and interrupting a turn are distinct operations; clearing must not imply an in-flight operation was stopped. On restart, query native goal state and reconcile before resuming. Avoid duplicate side effects, unrequested resumes and automatic budget increases.

## Latest Release Relevance

The official 0.172.0 release includes lazy startup of cached optional MCP servers, per-app-tool approval reviewer configuration, Bedrock setup/login support, and fixes to resume permissions and interrupted parent/child replies. Terminal navigation and command completion need no Telegram equivalent. Earlier releases expand remote and realtime workflows, which are lower priority for this bridge.

Generated client requests grew from 175 to 192 methods. Additions include streaming thread search, approved-plan preparation, memory reads, provider management and account-session switching. RPC availability does not prove end-to-end support. Account/provider switching needs separate authorization design.

## Delivery Order

1. Compatibility-test stable 0.172.0 in isolation, including existing text, image/file delivery, steering, approvals and reconnects. Check the updater timer before a drained, guarded deployment; retain rollback capability.
2. Implement both question paths. Test multiple questions, custom replies, duplicate/stale clicks, wrong users/topics, mention-only groups, secrets, interruption, resolved requests and send failures.
3. Add session supervision and native goals. Test multi-turn progress, fairness, usage/status, pause/resume, clear during a turn, budget exhaustion and crash recovery without duplicate effects.
4. Add native Plan mode and model-derived reasoning options, then richer progress and thread search/fork.

Use protocol fixtures plus a disposable bound Telegram topic for acceptance. Build success or healthy deployment alone does not prove question replies or goal continuation.
